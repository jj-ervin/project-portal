## This bounded change

The Git Explorer queries only explicit `folder` resources on the selected project, up to ten at a time. The server validates the same-origin POST and Windows path, requires an existing repository root folder, runs fixed Git read commands with optional locks disabled, and returns at most 100 working tree entries. No repository scan, command input, write operation, or cross-project provider session is added. Reopen Git to refresh the snapshot. The browser-local version 1 project schema is unchanged. Test output and temporary fixtures now use this repository's ignored `.scratch` directory.

Verification: before the change, ProPro unit tests passed 29/29, ProPro Chromium browser tests passed 25/25, and Cockpit GUI unit tests passed 14/14. After the change, ProPro unit tests passed 31/31 and the full Chromium browser suite passed 27/27. Cockpit GUI's package distribution test passed 1/1. The browser suite exposed an Agent Manager refresh race; the fix preserves an unfinished custom-agent form and has its own browser regression check. These automated results do not establish owner visual acceptance, successful external IDE launches, or live agent execution beyond the existing conversation checks.

## November 11 follow-up: explicit VS Code launch

A linked project folder now offers **Open in VS Code** in Resources and its center entry tab. The loopback server accepts only a same-origin POST with the validated folder connection, checks the folder exists, finds `Code.exe` in standard per-user or Program Files locations, and starts it with that folder as one argument. There is no arbitrary command field or automatic launch. The server reports a missing folder, missing installation, or launch failure. The action does not inspect VS Code sessions or give ProPro editing authority. The installed executable was detected locally during development; packaged Windows behavior and other-machine installations remain acceptance checks. Focused unit and browser checks use a launch stub so tests never open the editor. After this follow-up, the full ProPro unit suite passed 33/33 and the full Chromium browser suite passed 28/28.

Local launch acceptance, November 11: with ProPro running on loopback, an explicit request for the linked `C:\dev\project-portal` folder returned `opened: true`. Windows then showed a VS Code window titled `Welcome - project-portal - Visual Studio Code`. The temporary ProPro server was stopped after verification. This confirms this machine's live launch path; packaged-app and other-machine acceptance remain open.

## November 11 follow-up: first DW-02 read-only run

The bottom Agent runs tab can start one explicit Codex run from the selected project's linked folder. It reuses the existing `runCodex` invocation with `--sandbox read-only`, `--ignore-user-config`, and disabled approvals. The request records project identity, folder, instructions, status, progress, result or failure, and timestamps in ignored `.propro/runs.json`. The user can observe progress, stop a run, revisit a saved result, and see an interrupted state after server restart. The server validates the same-origin request and folder path and rejects concurrent runs. The browser's project records are local, so the server cannot independently prove that a submitted folder belongs to the submitted project; this is an association from the explicit UI selection, not an authorization boundary.

The result is Codex's final text, not a raw command log or verified artifact manifest. No write-capable run, automatic role routing, provider cost enforcement, external session discovery, Git/test result attachment, or delivery-gate update is included. The browser tests mock the provider response and do not incur an agent run. The full ProPro suite passed 36/36 unit and 29/29 Chromium browser checks, including narrow-layout and automated accessibility rules for the run panel.

Live local acceptance, November 11: a read-only run against `C:\dev\project-portal` used an isolated `.scratch` run store and asked Codex to read only `README.md`. The service returned `succeeded`, saved the result, and the result correctly identified the `ProPro` heading and described the project. The temporary server was stopped after verification. This confirms the local CLI path and persistence on this machine; it does not test a packaged install, paid-account policy, write approvals, or a project record selected in the owner's browser profile.

Packaging check before sync, November 11: the Windows portable build completed under ignored `.scratch/release`. Its unpacked app includes the Bootdog workflow files and all new agent/Git/IDE modules; the unpacked server returned HTTP 200 for the dashboard, workflow page, Agent runs script, runs API and Bootdog API. The packaged desktop window itself was not exercised. ProPro unit tests passed 36/36 after the packaging change; the most recent full browser suite passed 29/29 before the packaging-only edits.
